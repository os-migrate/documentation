= Using a custom nbdkit plugin

[role="_abstract"]
By default, the VMware Migration Kit uses the nbdkit `vddk` plugin to transfer VMware virtual machine disks. In some scenarios, you might want to bypass VDDK and use an alternative nbdkit plugin, for example a third-party plugin that implements the NBD or NFC protocol.

The `custom_nbdkit_plugin` variable specifies the absolute path to a custom nbdkit plugin shared library (`.so` file) on the conversion host.

== Configuration

Set the `custom_nbdkit_plugin` variable to the full path of your plugin:

[source,yaml]
----
custom_nbdkit_plugin: /home/cloud-user/nbdkit-nfc-plugin.so
----

When this variable is set:

* nbdkit is invoked with your custom plugin instead of `vddk`.
* VDDK-specific parameters (`libdir`, `compression`, `transports`, and disk name) are omitted from the nbdkit command.
* Only the common parameters (`server`, `user`, `password`, `thumbprint`, `vm`, and `snapshot`) are passed.

== Example usage

[source,yaml]
----
- name: Import VM with custom nbdkit plugin
  import_role:
    name: os_migrate.vmware_migration_kit.import_workloads
  vars:
    import_workloads_conversion_host_ssh_private_key: /path/to/key
    import_workloads_src_conversion_host: conversion-host.example.com
    import_workloads_src_conversion_host_username: cloud-user
    import_workloads_filters:
      - vmware_name: my-vm
    import_workloads_vddk_thumbprint: "AA:BB:CC:DD..."
    custom_nbdkit_plugin: /home/cloud-user/go-nfc/plugins/nbdkit-nfc/nbdkit-nfc-plugin.so
----

== Requirements

* The custom plugin `.so` file must be present on the conversion host at the specified path.
* The plugin must be compatible with nbdkit and accept the parameters passed by the VMware Migration Kit.
* Leave `custom_nbdkit_plugin` empty or unset to use the default VDDK plugin.

[NOTE]
====
When using a custom plugin, ensure that it supports the VMware connection parameters and snapshot handling required for migration.
====

[id="ref_vmw-nbd-multi-connection-tuning"]
== Multi-connection tuning

You can tune the disk transfer with extra options for the nbdkit server and for `nbdcopy`. With multiple parallel
connections to the source datastore and multiple in-flight requests, the transfer of large disks can use more of the
available bandwidth. Both options are empty by default, which leaves the commands unchanged.

[cols="2,3,2",options="header"]
|===
| Variable | Description | Example values

| `nbdkit_options`
| Dictionary of extra parameters appended to the nbdkit server command as `key=value` tokens. Applied only when
`custom_nbdkit_plugin` is set.
| `multiconn: true`, `sessions: 8`, `pipeline: 16`

| `nbdcopy_options`
| Dictionary of extra flags appended to the `nbdcopy` command as `--key=value` tokens. Applied with any plugin.
| `connections: 16`, `requests: 64`
|===

The `import_workloads` role passes these variables to the `migrate` module as `import_workloads_nbdkit_options` and
`import_workloads_nbdcopy_options`.

[IMPORTANT]
====
* With the built-in `vddk` plugin, `nbdkit_options` is ignored.
* When `nbdkit_options` is set together with a custom plugin, the migration waits a few seconds for the backend
connection of the plugin to open before it starts `nbdcopy`.
* The keys of both dictionaries are rendered in sorted order, so the generated commands are deterministic.
====

.Example usage
[source,yaml]
----
- name: Migrate VM with multi-connection tuning
  os_migrate.vmware_migration_kit.migrate:
    dst_cloud: "{{ my_dst_cloud_auth_details }}"
    user: "{{ my_vcenter_username }}"
    password: "{{ my_vcenter_password }}"
    server: "{{ my_vcenter_hostname }}"
    vmname: "{{ target_vm_name }}"
    osmdatadir: "{{ os_migrate_data_directory_path }}"
    vddkpath: "{{ global_vddk_path }}"
    # nbdkit_options take effect only with a custom plugin
    custom_nbdkit_plugin: "/usr/lib64/nbdkit/plugins/nbdkit-custom-plugin.so"
    nbdkit_options:
      multiconn: true
      sessions: 8
      pipeline: 16
    nbdcopy_options:
      connections: 16
      requests: 64
  register: migrate_vm_output
----

The options have the following effect:

`sessions`:: Number of parallel NBD connections that nbdkit opens to the source datastore. Values such as 8 to 16 can
improve the throughput for large disks.
`pipeline`:: Request pipelining within each session. A value such as 16 allows multiple in-flight requests per
connection.
`connections`:: Number of parallel connections that `nbdcopy` uses to read from nbdkit. Typically equal to or greater
than the nbdkit `sessions` value.
`requests`:: Maximum number of concurrent in-flight requests in `nbdcopy`. Higher values, such as 64, can saturate the
available bandwidth.

Tune the values to your network capacity and datastore performance. Start with conservative values and increase them
gradually while monitoring the transfer speed.
