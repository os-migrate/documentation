= Migrating workloads directly from the source hypervisor

[role="_abstract"]
Use NBD source migration to transfer volume data directly from the source hypervisor to the destination conversion host,
bypassing the source conversion host. For how this works, see xref:con_osts-nbd-source-migration[]. For the standard
workload migration procedure, see xref:proc_osts-migrating-workloads[].

.Prerequisites

* A conversion host is deployed in the destination cloud. See xref:proc_osts-deploying-conversion-hosts[].
* The destination conversion host has direct network connectivity to the source hypervisors on the `qemu-nbd` ports
(10809 and higher by default).
* The workloads to migrate are in the `SHUTOFF` state at export time. The `import_from_hypervisor` role checks the
status recorded in `workloads.yml` by `export_workloads`, so stopping an instance after export is not sufficient.
* The `os_migrate.os_migrate` collection 1.1.0 or later, with `openstacksdk` 4.21.0 or later and the Python `jmespath`
library.

.Procedure

. Export the workload metadata from the source cloud:
+
[source,bash]
----
$OSM_CMD $OSM_DIR/playbooks/export_workloads.yml
----

. Enable NBD direct mode for each workload to migrate this way, by adding the `use_nbdkit_direct` flag to the
`_migration_params` section of the workload in `workloads.yml`:
+
[source,yaml]
----
- _info:
    id: abc-123-def-456
    hypervisor_hostname: compute-01.example.com
    status: SHUTOFF
  params:
    name: my-instance
  _migration_params:
    use_nbdkit_direct: true
----
+
The `hypervisor_hostname` field is populated by `export_workloads`. You can set `use_nbdkit_direct` after export, or set
it in your workload definitions before export.

. Spawn the `qemu-nbd` processes on the source hypervisors:
+
[source,bash]
----
$OSM_CMD $OSM_DIR/playbooks/import_from_hypervisor.yml
----
+
For each workload marked `use_nbdkit_direct: true`, the `import_from_hypervisor` role verifies that the instance is
`SHUTOFF`, connects to the hypervisor over SSH, discovers all disk files in
`/var/lib/nova/instances/<uuid>/` (such as `disk`, `disk.eph0`, and `disk.eph1`), inspects each disk with `qemu-img
info` to detect its format and size, spawns one `qemu-nbd` process per disk on sequential ports starting from 10809, and
updates `workloads.yml` with the `nbdkit_disks` list. Run this role after exporting workloads and before importing them.

. Verify that the `nbdkit_disks` list was added to each workload in `workloads.yml`:
+
[source,yaml]
----
- _info:
    id: abc-123-def-456
    hypervisor_hostname: compute-01.example.com
  params:
    name: my-instance
  _migration_params:
    use_nbdkit_direct: true
    nbdkit_disks:
      - device: "/dev/vda"
        uri: "nbd://compute-01.example.com:10809"
        port: 10809
        size: 10
        bootable: true
      - device: "/dev/vdb"
        uri: "nbd://compute-01.example.com:10810"
        port: 10810
        size: 10
        bootable: false
----
+
Each entry represents one disk: `device` is the device name on the destination instance, `uri` is the NBD URI to connect
to, `port` is the `qemu-nbd` port number, `size` is the disk size in GB detected from `qemu-img info`, and `bootable`
indicates whether the disk is the boot disk.

. Migrate the workloads:
+
[source,bash]
----
$OSM_CMD $OSM_DIR/playbooks/import_workloads.yml
----
+
For workloads marked `use_nbdkit_direct: true`, `import_workloads` reads the `nbdkit_disks` list, creates one destination
volume per disk, attaches the volumes to the destination conversion host, copies each disk from its NBD URI with
`nbdcopy`, detaches the volumes, and creates the instance with the new volumes.

To customize the role behavior, set the variables described in xref:ref_osts-nbd-variables[].

[id="proc_osts-nbd-without-src-conversion-host"]
== Migrating without a source conversion host

When all the disks of the migrated workloads are local disks served by `qemu-nbd`, no source conversion host is
required. Disable the source conversion host explicitly, so that the playbooks do not wait for it or fail because it is
missing. Only the destination conversion host is required in this mode.

.Procedure

. Set the following variables in your variables file, or pass them with the `-e` option:
+
[source,yaml]
----
os_migrate_deploy_src_conversion_host: false
os_migrate_link_conversion_hosts: false
os_migrate_requires_src_conversion_host: false
----
+
With these values, `deploy_conversion_hosts.yml` deploys only the destination conversion host and skips the link step,
and `import_workloads.yml` tolerates a missing source conversion host. For the description of each variable, see
xref:ref_osts-nbd-variables[].

. Ensure that the source hypervisor is reachable over SSH. The `import_from_hypervisor` role delegates the `qemu-img`
and `qemu-nbd` tasks to the compute node reported by Nova as `hypervisor_hostname`, and takes the SSH connection
settings, such as `ansible_user` or `ansible_ssh_user`, from the inventory entry of that host. If you cannot add the
hypervisor to your inventory, set the SSH user for the delegated tasks:
+
[source,yaml]
----
os_migrate_hypervisor_ssh_user: root
----

. Run the `import_from_hypervisor.yml` and `import_workloads.yml` playbooks as described earlier in this procedure.

[id="proc_osts-nbd-mixed-migration"]
== Migrating local disks and Cinder volumes together

A single `import_workloads` run can migrate a workload that has both local disks, such as an image-backed boot disk or
ephemeral disks, and attached Cinder volumes. The migration uses two transfer methods:

* `nbdcopy` from the `qemu-nbd` export on the source hypervisor, for the local disks.
* The conversion host path, for the attached Cinder volumes.

.Prerequisites

* The source hypervisor is reachable, so that `import_from_hypervisor` can spawn `qemu-nbd`.
* A source conversion host and a destination conversion host are deployed and linked. Do not disable the source
conversion host for mixed migrations.

.Procedure

. Stop the source instance before you export it:
+
[source,bash]
----
openstack server stop <instance_name>
----

. Export the workload and enable NBD direct mode in the `_migration_params` section of the workload in `workloads.yml`:
+
[source,yaml]
----
- _info:
    id: <instance_id>
    status: SHUTOFF
  params:
    name: my-vm
    volumes:
      - _info:
          id: <cinder_volume_id>
        params:
          name: data-volume
  _migration_params:
    use_nbdkit_direct: true
    boot_disk_copy: true
----

. Run the `import_from_hypervisor.yml` and `import_workloads.yml` playbooks as described earlier in this procedure.
+
The import copies the local disks directly from the source hypervisor with `nbdcopy`, copies the attached Cinder
volumes through the conversion hosts, and creates the destination instance with all disks attached.

The volume map of a workload is built from the first available source, in this order:

. `nbdkit_disks`: the actual disk sizes detected by `import_from_hypervisor`, which is the most accurate source.
. `volumes`: the Cinder volumes attached to the instance.
. Ephemeral disks: size estimates based on the flavor of the instance.

Each disk served by `qemu-nbd` is tagged with `transfer_method: "nbdcopy"` in the volume map. Cinder volumes exported
through the source conversion host default to the `qemu-img` conversion host path. This tagging lets a single migration
handle both transfer types.

[id="proc_osts-nbd-manual-hypervisor-preparation"]
== Preparing the hypervisor manually

To prepare the hypervisor without the `import_from_hypervisor` role, spawn the `qemu-nbd` processes yourself and update
`workloads.yml`.

.Procedure

. Locate the instance directory on the hypervisor:
+
----
/var/lib/nova/instances/<uuid>/
├── disk          # Boot disk
├── disk.eph0     # Ephemeral disk 0 (if present)
├── disk.eph1     # Ephemeral disk 1 (if present)
└── disk.info     # Metadata file (not used)
----

. Inspect each disk format:
+
[source,bash]
----
qemu-img info /var/lib/nova/instances/<uuid>/disk
----

. Start `qemu-nbd` for each disk, using read-only mode and sequential ports:
+
[source,bash]
----
# Boot disk on port 10809
sudo qemu-nbd -f qcow2 -p 10809 --read-only \
  /var/lib/nova/instances/<uuid>/disk

# First ephemeral disk on port 10810 (if present)
sudo qemu-nbd -f qcow2 -p 10810 --read-only \
  /var/lib/nova/instances/<uuid>/disk.eph0
----

. Update `workloads.yml` with the `nbdkit_disks` structure shown earlier, then continue with the standard
`import_workloads` step.

[id="ref_osts-nbd-security-considerations"]
== Security considerations

When using NBD source migration:

* Ensure the instance is `SHUTOFF` before `qemu-nbd` starts. The `import_from_hypervisor` role enforces this check. To
stop workloads automatically, set `os_migrate_workload_stop_before_migration: true`.
* Keep `qemu-nbd` in read-only mode to prevent accidental writes to the source disks, by keeping
`os_migrate_nbdkit_readonly: true`.
* Over untrusted networks, use the SSH protocol for encrypted transfers, by setting `os_migrate_nbdkit_protocol: ssh`
and `os_migrate_nbdkit_ssh_user`.
* `qemu-nbd` binds to all interfaces by default. Use firewall rules on the hypervisor to allow only the destination
conversion host to connect to ports 10809 and higher.
