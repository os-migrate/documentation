=== Multi-Connection Tuning for NBD Transfer

When using a custom nbdkit plugin, you can enable multi-connection parameters to improve disk transfer performance. This feature allows nbdkit to establish multiple parallel connections to the source VMware datastore and nbdcopy to use multiple concurrent requests.

==== Configuration Parameters

Two new optional parameters control multi-connection behavior:

[cols="2,3,2",options="header"]
|===
| Parameter | Description | Example Values

| `nbdkit_options`
| Dictionary of extra parameters appended to the nbdkit server command as `key=value` tokens. Only applied when `custom_nbdkit_plugin` is set.
| `multiconn: true`, `sessions: 8`, `pipeline: 16`

| `nbdcopy_options`
| Dictionary of extra flags appended to the nbdcopy command as `--key=value` tokens.
| `connections: 16`, `requests: 64`
|===

[IMPORTANT]
====
* `nbdkit_options` are *only honored* when `custom_nbdkit_plugin` is configured. With the built-in vddk plugin, these options are ignored.
* When `nbdkit_options` are set with a custom plugin, the migration module waits 10 seconds for the backend connection to establish before starting nbdcopy.
* Both parameter dictionaries are rendered in sorted key order for deterministic command generation.
====

==== Example Usage

[source,yaml]
----
- name: Migrate VM with multi-connection tuning
  os_migrate.vmware_migration_kit.migrate:
    dst_cloud: "{{ my_dst_cloud_auth_details }}"
    user: "{{ my_vcenter_username }}"
    password: "{{ my_vcenter_password }}"
    server: "{{ my_vcenter_hostname }}"
    vmname: "{{ target_vm_name }}"
    osmdatadir: "{{ os_migrate_data_directory_path }}"
    vddkpath: "{{ global_vddk_path }}"
    # Custom plugin is required for nbdkit_options to take effect
    custom_nbdkit_plugin: "/usr/lib64/nbdkit/plugins/nbdkit-custom-plugin.so"
    nbdkit_options:
      multiconn: true
      sessions: 8
      pipeline: 16
    nbdcopy_options:
      connections: 16
      requests: 64
  register: migrate_vm_output
----

==== Performance Considerations

* **sessions**: Controls the number of parallel NBD connections nbdkit opens to the source datastore. Higher values (e.g., 8-16) can improve throughput for large disks.
* **pipeline**: Enables request pipelining within each session. Values like 16 allow multiple in-flight requests per connection.
* **connections**: Sets how many parallel connections nbdcopy uses to read from nbdkit. Should typically match or exceed the nbdkit sessions value.
* **requests**: Controls the maximum number of concurrent in-flight requests in nbdcopy. Higher values (e.g., 64) can saturate available bandwidth.

Test different combinations based on your network capacity and datastore performance. Start with conservative values and increase gradually while monitoring transfer speeds.
=======

=== Configuring nbdkit Direct Mode Migration

When migrating workloads using nbdkit direct mode (streaming disks directly from the hypervisor's `qemu-nbd`), no source conversion host is required. You must explicitly disable the source conversion host in your configuration to prevent playbook failures.

==== Required Variables

Set the following variables in your `vars.yml` or via command-line `-e` flags:

[source,yaml]
----
# vars.yml
os_migrate_deploy_src_conversion_host: false
os_migrate_link_conversion_hosts: false
os_migrate_requires_src_conversion_host: false
----

.NBDkit Direct Mode Variables
|===
|Variable |Value |Effect

|`os_migrate_deploy_src_conversion_host`
|`false`
|The `deploy_conversion_hosts.yml` playbook deploys only the destination conversion host, not a source one.

|`os_migrate_link_conversion_hosts`
|`false`
|Skips the conversion-host link step, which otherwise waits for a source conversion host to become reachable over SSH.

|`os_migrate_requires_src_conversion_host`
|`false`
|The `import_workloads.yml` playbook tolerates a missing source conversion host instead of failing the run.
|===

NOTE: Only the destination conversion host is required in nbdkit direct mode.

==== Hypervisor Connection Configuration

The nbdkit direct mode role delegates `qemu-img` and `qemu-nbd` tasks directly to the source hypervisor. The SSH connection settings are taken from the hypervisor's inventory entry.

Ensure the compute node reported by Nova as `hypervisor_hostname` is present in your Ansible inventory with the correct credentials (`ansible_user` or `ansible_ssh_user`).

If you cannot add the hypervisor to your inventory, override the SSH user for delegated tasks:

[source,yaml]
----
os_migrate_hypervisor_ssh_user: "root"  # or "stack", etc.
----

Leaving `os_migrate_hypervisor_ssh_user` empty (default) uses the inventory settings.

==== Instance State Requirement

Instances must be fully shut down before migration in nbdkit direct mode. If an instance is still running or its disk images are locked, `qemu-img` reports a virtual size of zero, and the migration will fail with a clear error message.

Ensure all source instances are stopped before running the import playbook.

== Changes in v2.3.0

The v2.3.0 release introduces several important features and improvements for VMware to OpenStack migrations.

=== Custom nbdkit Plugin Support

You can now bypass the VMware VDDK plugin by configuring a custom nbdkit plugin. This allows alternative data transfer methods without requiring the proprietary VMware VIX DiskLib.

When using a custom nbdkit plugin:

* The VMware VIX DiskLib (libdir) check on the conversion host is automatically skipped
* The migration process waits for the custom nbdkit plugin backend connection to open before starting nbdcopy

Refer to the `prelude` role argument specifications for configuration details.

=== Enhanced nbdkit and nbdcopy Configuration

You can now control nbdkit and nbdcopy multi-connection options through dictionary variables:

* `sessions`, `pipeline`, and `multiconn` options for nbdkit
* `connections` and `requests` options for nbdcopy

These settings allow fine-tuning of parallel data transfers for improved migration performance.

=== Heat Stack Integration

Migrated instances are now wrapped in Heat orchestration stacks. This provides:

* Support for migration rollbacks using Heat's adopt/abandon functionality
* Automatic retry of instance creation on rollback status codes
* Better tracking and management of migrated resources

=== Configuration Variable Changes

The following configuration changes were made:

* `openstack_insecure` moved under the `dst_cloud` variable scope
* `esxi_hostname` is now optional
* Added `block_storage_api_version` configuration option

=== Boot Volume Handling Improvements

The migration process now:

* Looks up Cinder boot volumes by UUID for more reliable volume identification
* Treats an in-use boot volume on an active instance as a successful migration state
* Discovers all disk keys from `disk_info` when building `data_volume_ids`

=== Security and Reliability

* vCenter credentials are now removed from migration log files to prevent credential exposure
* Fixed shell quoting issues that caused failures when VM names contained spaces in virt-v2v-in-place operations
